# Local batch review

Open **Leads → Batch review**. The screen stages a CSV with a header row or a JSON array of flat lead records. Maximum: 5 MiB, 5,000 rows, 200 columns. Common headers include `lead_id`, `source_record_id`, `property_address`, `property_city`, `property_state`, `property_zip`, `owner_name`, `asking_price`, `bedrooms` and `lot_sqft`. Prefix a known canonical identifier with a `Lead ID` or `PBK Lead ID` header, not a generic `ID` column. Keep ZIPs and other identifiers as strings in JSON to preserve leading zeroes. Unknown fields are displayed as not mapped. Asking price is not a sold price or an ARV input.

- **New:** No supplied canonical ID and no address or in-batch duplicate candidate. This is not permission to create a record.
- **Matches:** One exact PBK lead ID, with no differing saved values or identity conflicts.
- **Conflicts:** Address-only candidates, unknown or ambiguous IDs, potential duplicates, or differing saved fields. Saved values, including manual edits, take precedence.
- **Invalid:** Malformed row or unsupported values in known fields. An unreadable file is rejected; recoverable row errors appear in the queue.

In the browser, the file and review marks stay in the current page. Real files are preview-only in the browser. The app reads `GET /api/leads/batch-review-roster` only after the user starts a review. This endpoint combines the workspace's Postgres profiles and bridge-only leads by canonical ID. It fails closed if either source is unavailable, a source has ambiguous IDs, or the combined roster exceeds 10,000 leads. Address hints are deliberately conservative; they do not automatically identify or merge leads.

BatchLeads property facts, owner and mailing details, valuation and prior-sale figures, and foreclosure fields have separate labels. `Estimated Value` and `Last Sale Price` are not ARV or asking price. Mailing city and state are not property location fields. Each of `Phone 1` through `Phone 5` keeps its own number, DNC value, and type. Blank DNC stays Unknown, and metadata without a number or contradictory flags for the same number make a row invalid. Saved flags are compared by normalized phone number, not by slot.

Use **Shared phones** to see which property rows use the same normalized number. The preview shows one potential contact slot per number, not one per row or channel. A positive DNC flag anywhere in the file (including excluded rows), on a saved lead, or in the workspace DNC snapshot blocks that number across the batch. An unknown flag is not a candidate. Sample apply considers only confirmed eligible rows and does not replace the stored per-row values.

The bridge's outbound Telnyx call and SMS paths share the Postgres phone reservation. Both confirmation flows register the phone plan with the saved lead IDs before publishing the leads in the same transaction. The plan enrolls only numbers associated with confirmed rows; a DNC flag on an excluded row still blocks a shared number. Failed registration or lead persistence rolls back both. One workspace phone has one enrollment: overlapping batches are rejected, replay cannot reset reservations, and a different lead cannot claim the slot. A new batch lead cannot use an unregistered alternate number. Non-batch numbers keep their existing behavior when shared safety storage is available.

The real operator-only bridge contract is `POST /api/leads/batch-apply`. It is not available through the team proxy or the browser preview. Direct bridge bearer authentication is required. Use `mode: "preview"` with `name`, `contents`, and the exact `reviewedRows` array to get aggregate counts and a review token in a read-only transaction. Real writes remain disabled unless `PBK_BATCH_APPLY_ENABLED=true` is explicitly set. When enabled, `mode: "apply"` requires `confirmed: true`, the preview's `reviewToken`, and the same file and selection. Any change to the saved roster or phone safety snapshot requires a new preview. The route writes lead profiles and phone enrollment only; it does not create approvals, schedule campaigns, or call any provider. Candidate status is not permission to contact.

The bridge commits an enrolled phone's reservation before dispatch, then checks DNC again under the same row lock used for opt-outs. A later DNC flag takes priority, even over a spent reservation. Once reserved, the slot is not retried after a timeout, crash, or ambiguous provider result. This guarantees at most one dispatch attempt, not delivery. DNC updates observed after a request has already started cannot recall it. An unavailable database or invalid destination blocks outbound dispatch instead of falling back to memory.

`npm run test:batch-phone-dispatch` uses synthetic phones and provider callbacks. It uses a temporary embedded PostgreSQL database by default. Set `PBK_BATCH_TEST_DATABASE_URL` to a dedicated loopback database named `pbk_batch_phone_test` to exercise separate connections against a native PostgreSQL server.

`npm run test:batch-apply` rehearses the real operator contract against synthetic embedded PostgreSQL, including a read-only preview, disabled writes, stale confirmation, rollback, exact lead binding, and stubbed call and SMS dispatch.

`npm run dev:batch-review` starts a localhost preview with a synthetic roster at `http://127.0.0.1:5190/leads/batch-review`. Download the [bundled sample](http://127.0.0.1:5190/batch-review-fixture.csv), mark a New or Match row reviewed, and choose **Apply reviewed sample rows**. The confirmation shows the eligible counts and the conflicts, invalid rows, and unreviewed rows that will be skipped. The result reports created, updated, unchanged, and skipped rows.

Only the exact bundled CSV enables Apply. The localhost server uses its own copy of that file, rechecks against the saved fixture roster, requires an explicit confirmation and current revision, and rejects stale or replayed requests. Matched rows only fill blank mapped fields or unused phone slots; saved values and per-number DNC flags are retained. Conflicts and invalid rows are never written. The synthetic workspace lives in `.pbk-local/batch-review-sample-postgres` and persists across preview restarts. Neither the preview nor the apply engine invokes a real bridge write or outreach.

`npm run test:batch-review` checks parsing, classification, and non-destructive apply planning. `npm run test:batch-review-browser` checks review and sample apply on desktop Chromium and iPhone-sized WebKit using isolated temporary databases and a stub call/text callback.
